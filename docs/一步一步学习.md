# 一步一步学习 Notice Hub

先操作一遍，再跟踪代码。每次只围绕一个问题：请求怎么进来、规则在哪里、结果怎么验证。下面的顺序与本项目实际实现一致，可以直接对照IDEA中的文件阅读。

## 第1步：体验业务，建立预期

访问线上系统时，使用管理员分配的账号。若要完整练习不同角色，在自己的开发环境中按 [本地开发与调试](SETUP.md) 初始化四个演示账号，密码由部署者自行设置；这些账号不会自动出现在共享线上实例中。

先用管理员看一遍六个页面，再用员工登录。员工的导航只有工作台、通知中心和个人设置；编辑还可以发布通知。打开一条由其他编辑创建的通知，自己没有编辑或删除入口。

这样做的原因：代码需要实现可描述的业务规则。“系统能登录”只是认证的起点，权限控制还要回答用户可以对哪些对象做哪些操作。对照 `需求与设计.md` 的角色矩阵，就能知道接下来的代码为什么存在。

## 第2步：从用户、角色、权限推导表

打开 `backend/src/main/resources/db/migration/V1__initial_schema.sql`。先看五张权限相关表：

| 表 | 它回答的问题 |
|---|---|
| app_user | 系统里有哪些账号？是否启用？ |
| app_role | 系统里有哪些职责组合？ |
| app_permission | 哪些操作可以单独授权？ |
| user_role | 一个用户被分配了哪些角色？ |
| role_permission | 一个角色拥有哪些权限？ |

一个用户可以是员工，也可以同时担任编辑，所以用户和角色通过关联表表达多对多关系。角色和权限同样如此。以后增加一种职责，只需要定义新角色和对应关系，不必在每个接口里不断增加用户名判断。

再看 `notice.created_by`：它记录这条通知的创建人。角色决定能否“编辑本人通知”，创建人字段决定“这是不是本人的通知”。两部分都需要检查。

如果你要在MySQL客户端观察，执行以下只读查询：

```sql
SELECT u.username, r.code
FROM app_user u
JOIN user_role ur ON ur.user_id = u.id
JOIN app_role r ON r.id = ur.role_id;

SELECT r.code AS role_code, p.code AS permission_code
FROM app_role r
JOIN role_permission rp ON rp.role_id = r.id
JOIN app_permission p ON p.id = rp.permission_id
ORDER BY r.id, p.id;
```

Flyway会在启动时按版本执行SQL，并保存执行历史。之后调整数据库结构应新增 `V2__...sql`，避免修改已经在数据库执行过的V1文件。

## 第3步：认识接口调用链

在IDEA中打开 `backend/pom.xml`，加载Maven项目，项目SDK选择17。找到 `NoticeHubApplication`，这是Spring Boot入口。

以“创建通知”为例，代码流向是：

```text
frontend/src/pages/Notices.vue 的 save()
→ frontend/src/state.js 的 api()
→ POST /api/notices
→ WebConfig 拦截器
→ NoticeController.create()
→ NoticeService.create()
→ NoticeMapper.insert()
→ MySQL notice 表
```

Controller接收请求并触发输入校验；Service判断业务是否允许并组织写入；Mapper执行SQL。分层后，修改“谁能创建通知”时能直接找到Service，调整字段校验时能找到DTO。

## 第4步：读懂登录发生了什么

打开 `AuthController` 和 `AuthService.login()`，再对照浏览器开发者工具的 Network 面板。输入账号密码，观察 `POST /api/auth/login`。

登录方法按顺序做这些事：

1. 规范化用户名，检查Redis里的失败次数。
2. 按用户名查询用户；使用 `PasswordEncoder.matches()` 核对密码。
3. 确认账号启用。
4. 调用 `StpUtil.login(userId)` 建立会话。
5. 保存登录审计，返回Token、有效期和安全的用户信息。

密码验证不能拿输入字符串和数据库值直接比较。数据库保存的是带盐哈希，`matches()`会使用哈希里记录的算法和参数进行验证。编码器在 `WebConfig.passwordEncoder()` 中设置为Argon2id，盐由成熟库自动生成。

首次示例账号由 `DemoInitializer` 写入。它只在显式开启演示初始化且用户表为空时执行，第二次启动不会重置密码。

## 第5步：理解后续请求如何识别用户

登录后，前端 `setAuth()` 把Token放入当前标签页的 `sessionStorage`。`api()`为后续请求加上：

```http
noticehub-token: Bearer <登录得到的Token>
```

打开 `WebConfig.addInterceptors()`：`/api/**`都要经过登录检查，明确放行登录和健康检查接口。`StpUtil.checkLogin()`根据Token确认登录身份，`access.current()`进一步查询账号是否还启用。

用Postman去掉Token再请求通知列表，应该返回401。复制一个随机字符串作为Token，仍然返回401。Token是后端识别会话的凭证，前端传一个用户名或用户ID无法替代它。

两小时有效期来自 `application.yml` 的 `sa-token.timeout: 7200`，自动续期关闭。Redis保存实际会话及TTL，退出时删除相应登录关系。

## 第6步：让身份变成操作权限

打开 `AccessService`。它实现Sa-Token的 `StpInterface`，通过 `AccessMapper` 查询用户的角色与权限。查询沿着 `user_role → role_permission → app_permission` 得到权限码。

再看 `NoticeService.create()` 中的：

```java
access.check("notice:create");
```

编辑拥有此权限，员工没有，所以同一个接口对两个账号会给出不同结果。后端每次从数据库查询当前权限，管理员撤销角色后，原Token下一个请求就受到新规则约束。

前端的 `can()`只控制按钮和导航的展示；后端 `access.check()`决定请求能否执行。可在Postman里用员工Token直接调用创建通知接口，验证403。

前端在切换页面、收到权限拒绝和定时同步时刷新个人权限，因此界面可能比后端规则稍晚更新；后端从下一次请求起就执行新权限。

## 第7步：检查这条通知是不是自己的

打开 `NoticeService.checkOwner()`：管理员具有 `notice:manage`，可以管理全部通知。编辑要先具有对应的本人修改或删除权限，再确认 `created_by`等于当前登录ID。

通知创建人取自 `StpUtil.getLoginIdAsLong()`，请求DTO里没有 `createdBy`。这保证创建人来自后端认证信息。客户端伪造这个字段，会被未知字段校验拒绝。

用 `editor` 创建通知，再用 `editor2` 的Token请求修改同一通知ID，应该返回403。两个账号同为编辑，数据归属依然不同，这就是横向越权检查。

## 第8步：读懂一次可靠的更新

通知详情返回 `version`。编辑时前端原样带回版本号，`NoticeMapper.updateVersion()`执行：

```sql
UPDATE notice
SET ..., version = version + 1
WHERE id = ? AND version = ? AND deleted = 0;
```

如果两个浏览器都读到版本0，第一人保存后变成版本1。第二人仍带版本0，更新影响行数为0，Service返回409并提醒刷新。这样能阻止“后保存覆盖先保存”。

删除通知采用 `deleted=1` 的逻辑删除，普通查询不再返回它；原数据仍可在数据库中追溯。界面和接口当前提供删除，数据恢复属于后续管理功能。

## 第9步：处理账号状态、密码和审计

看 `UserService.enabled()`：管理员停用账号时，既更新MySQL中的启用状态，也调用 `StpUtil.logout(userId)`注销该用户全部登录。两层处理让旧Token和重新登录都受到约束。

看 `AuthService.changePassword()`：先验证旧密码，再保存新哈希并注销全部会话。新密码生效后，需要重新登录。请先用临时账号练习，避免忘记自己修改的密码。

看 `AuditService`：记录操作人、操作类型、对象、结果和时间。业务写入和对应成功审计放在同一个数据库事务里；登录失败独立保存记录。数据库事务不能把Redis变成同一个事务资源，当前通过账号状态复查和每次读取权限来约束后续请求。

看 `Requests` 和 `GlobalExceptionHandler`：输入约束与业务异常统一转换成HTTP状态和JSON响应。400表示参数错误，401表示登录无效，403表示权限不足，404表示资源不存在，409表示重复或版本冲突，429表示请求受限。

## 第10步：看前端如何与后端配合

按 `main.js → App.vue → pages/Notices.vue → state.js` 的顺序阅读。

- `main.js`定义页面路由，在进入管理页面前检查当前用户权限。
- `App.vue`根据用户权限生成导航，放置全局确认弹窗和提示消息。
- 页面组件收集输入、显示列表、处理加载和错误状态。
- `state.js`统一加Token、发送JSON、处理401和403，把失败信息交给页面或提示组件。

通知正文使用Vue文本插值显示，不作为HTML执行。生产构建的静态资源复制到后端，浏览器访问同一个地址即可请求页面和API；开发模式中Vite通过代理转发 `/api`，避免依赖开放跨域配置。

## 第11步：自己重复验收

在项目目录执行：

```powershell
python scripts/verify.py
```

脚本向真实服务发送请求，使用MySQL和Redis检查持久化结果。它创建本轮专用的临时账号，测试后只按返回ID清理这些账号和通知；审计记录保留。报告写入 `docs/验收结果.md` 和 `docs/acceptance-results.json`。

有效期测试分两部分：检查实际会话TTL接近7200秒，再将专用测试凭证TTL改为1秒验证过期拒绝。它没有等待两小时再声称完成一次真实两小时运行。

Postman材料在 `docs/postman/`：导入集合和 `NoticeHub.environment.example.json`，将服务地址、测试用户名和密码填写到自己的私有环境中。登录请求会自动保存Token。按角色切换用户名后重新登录，即可比较相同请求的响应。导出到公开仓库前清空密码和Token。

## 下一次建议怎么学

第一轮先读到第5步，只解决“账号密码怎么变成登录状态”。把自己对这条链路的理解讲出来，再用断点验证。第二轮学习权限码和数据归属，第三轮看事务、版本冲突和验收脚本。每一轮都能在这个已经运行的系统里观察真实结果。
